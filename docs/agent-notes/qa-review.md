# QA review: persistent synthetic slice

Scope: `server/domain.mjs`, `server/db.mjs`, `server/index.mjs`, `server/worker.mjs`, `src/main.tsx`, and focused tests. Read-only review; no application files changed. `node --test tests/*.test.mjs` passed 7/7, but the cases below are not covered.

## Findings (priority order)

1. **P1: incorrect shelf answers can be recorded as matches.** `server/domain.mjs:60-67` treats proximity of `unfinished` and `yellow` as evidence of placement. Reproduction: `assessAnswer('Finished items on the blue shelf. Unfinished items stay on the floor near the yellow shelf.')` returns `matched`, although the unfinished items are on the floor. It also rejects the valid concise `Finished blue; unfinished yellow.` as `contradictory_placement` because the first fact is within 35 characters of `yellow`. Since a false match is the dangerous error here, avoid automatic `matched` for ambiguous relational phrasing. Use an explicit version-bound assessment contract with required relation/evidence and uncertainty fallback; add these two phrases, negatives, swaps, paraphrases, and Arabic/Urdu equivalents to the evaluation set. The current regex is suitable only as a narrow deterministic demo classifier, not a pilot assessment gate.

2. **P1: new publication leaves the prior version actionable.** `server/domain.mjs:93-96` inserts v4 as `published` without changing v3; `server/index.mjs:76-85` lists both assignments; `server/domain.mjs:110` still accepts an answer for v3. In-memory reproduction after publishing v4 showed both v3 and v4 in `published` state, and a new v3 answer was accepted. Define the supersession/withdrawal policy, atomically transition the former active publication when v4 is published, distinguish history from current worker tasks, and reject or explicitly handle stale-version uploads. Add a regression covering v3 pending work, v4 publication, old answer history, and a late v3 submission.

3. **P1/P2: the UI defeats server submission idempotency on retries or double clicks.** `src/main.tsx:196-200` creates a fresh `crypto.randomUUID()` every time the send handler runs, and the button has no in-flight guard. `server/domain.mjs:111-118` deduplicates only the same ID. Two sends of the same incomplete answer produced two attempts and two open clarifications. Keep one submission ID tied to a local answer draft until receipt or explicit new attempt; disable duplicate sends while pending; persist that ID with any offline outbox. Add a browser/API retry test asserting a single attempt/case after timeout and repeated send.

4. **P2: database foreign keys do not enforce tenant/site consistency.** `server/db.mjs:45-49` independently references publication and worker IDs; no composite key binds their `org_id` and `site_id` to the assignment. The DB accepted a Cedar assignment for `harbor-worker`, increasing Cedar's assigned metric from 30 to 31 (`server/domain.mjs:72-79`) even though that worker cannot read it. Similar independent references occur across dependent tables. Add composite unique parent keys and composite foreign keys for organization/site/parent relationships, plus insert-rejection tests for cross-tenant and cross-site references. API scoping is good but cannot substitute for data invariants in jobs/imports.

5. **P2: worker help requests are not idempotent or publication-state guarded.** `server/index.mjs:228-234` inserts an open clarification for every POST after only checking assignment ownership in the shared route. Retry after an uncertain response creates duplicate conversations; an assignment on a withdrawn/superseded publication can still receive help through this path. Add a client request ID and unique constraint, and apply an explicit current/historical help policy after checking publication state. Test repeated requests and stale assignments.

## Other verification gaps

- The tests cover a single happy-path preparation job; no stale lease/restart, concurrent process/publish, failed synthetic preparation, or replay/concurrency tests (`server/worker.mjs:6-41`, `tests/api.test.mjs`).
- `submitAnswer` loads `snapshot_json` but calls `assessAnswer(answerText)` without the publication rubric (`server/domain.mjs:106-113`). That is truthful only while every processable publication uses the one canonical synthetic question; before noncanonical sources are enabled, bind assessment to the exact frozen version and test it.
- The server's demo profile exchange is intentionally unauthenticated (`server/index.mjs:110-121`) and the API/worker listen on loopback. Preserve that local-only boundary. Do not expose this build as an authenticated tenant service or infer production security from the passing denial tests.
